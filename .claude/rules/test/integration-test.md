# 統合テスト設計

統合テストは、複数の実クラスがクリーンアーキテクチャの層をまたいで協調する際に、単体テストでは検出できないクラス間のインタラクション不具合を検出するためのテストである。

このドキュメントは統合テストのシナリオ選定基準と構造パターンを定める。
配置・モック境界・手動ワイヤリング等の基本ルールはテスト要件仕様 (test.md) に従う。

---

## 単体テストとの責務分離

| 観点 | 単体テスト | 統合テスト |
| --- | --- | --- |
| テスト対象 | 単一クラスの内部ロジック | 複数の実クラス間のインタラクション |
| 依存の扱い | 全依存をモック | Port (Repository / Integration) のみモック |
| 検証する正しさ | 入力 → 出力の変換ロジック | クラス間のデータ受け渡し・集約計算・エラー伝播 |
| 失敗が示すもの | 単一クラスのバグ | クラス間の結合バグ、ビジネスルールの組み合わせバグ |

原則: 単体テストで検証済みの単一クラス内部ロジックを統合テストで重複検証しない。
統合テストが検証すべきは「正しいクラスが、正しい順序で、正しい引数で呼ばれ、正しいビジネス結果を生む」ことである。

---

## シナリオ選定基準

### カテゴリ A: ビジネスロジック統合 (最優先)

複数の実クラスが協調して、要件で定義されたビジネス上の正しい結果を生み出すことを検証する。
単体テストでは各クラスが正しく動作することしか保証できず、組み合わせ後の結果が要件通りかは統合テストで初めて保証される。

#### A-1: クロスエンティティ集約/算出

複数の子エンティティ/レコードを集約し、計算された値 (集計、平均、スコア等) が要件通りであるかを検証する。

**選定条件**:
- UseCase または Application Service が複数の Repository から取得したデータを集約・計算する
- 計算ロジックが複数のクラスにまたがっており、単体テストの組み合わせでは漏れが生じる可能性がある

**検証すべきこと**:
1. 集約対象が 0 件のときに要件通りの値 (0、null、デフォルト値等) を返す
2. 集約対象が 1 件のときに単純なケースで正しく動作する
3. 集約対象が複数件のときに計算ロジック (平均、合計、最大値等) が正しく動作する
4. 条件フィルタリングがある場合、フィルタ後の集合に対して計算が行われる

#### A-2: ビジネスルール合成

複数の Application Service / Domain Service が適用するルールの組み合わせが正しく動作するかを検証する。

**選定条件**:
- UseCase が複数のルール関数・サービスを順次または条件分岐で呼び出す
- ルール A とルール B の組み合わせによって最終的な判定結果が決まる
- 状態ハッシュ・キャッシュ・スロットリング等のサブシステムとルール評価が連携する

**検証すべきこと**:
1. 全ルールが通過する (正常) 条件で期待する出力が得られる
2. 特定のルールが拒否する条件で期待する出力 (除外、スキップ等) が得られる
3. キャッシュ/ハッシュが一致する場合に処理がスキップされる
4. 複数の独立したルール評価結果が正しく集約される (AND/OR 等)

#### A-3: 状態遷移の連鎖

あるエンティティの状態変更が、関連エンティティに正しく波及するかを検証する。

**選定条件**:
- UseCase の実行によって複数のエンティティが更新される
- 更新の内容や条件が前のエンティティの状態に依存している

**検証すべきこと**:
1. 連鎖する更新が全て実行される (更新漏れがない)
2. 更新内容が先行する操作の結果に正しく依存している
3. 先行操作が失敗した場合、後続の更新が実行されない

---

### カテゴリ B: 認可チェーン統合

UseCase → Authorization Service → Resolver Service / Repository の多段呼び出しチェーン。単体テストでは Authorization Service をモックしているため、実チェーンの正しさが未検証。

**選定条件**:
- UseCase → Authorization Service → Resolver Service / Repository の多段呼び出しチェーンが存在する

**検証すべき 3 パターン** (全て必須):
1. **認可通過**: 実認可チェーンが通過し、副作用 (save / update / delete) が正しい引数で実行される
2. **認可拒否**: 実認可チェーンが拒否し、`AccessDeniedError` がスローされ、副作用が一切発生しない
3. **前処理順序**: リソース存在チェック (findById) と認可チェックの実行順序が仕様通りである

---

### カテゴリ C: パイプライン統合

複数の UseCase を直列に実行する、または UseCase が実 Domain Service のアルゴリズムと連携するケース。

**選定条件**:
- UseCase A の出力が UseCase B の入力になる直列パイプラインが存在する
- UseCase が Domain Service の計算結果 (フィルタリング、スコアリング、ハッシュ計算等) を Port メソッドの引数として渡す

**検証すべきこと**:
1. **データ受け渡し**: ステップ N の出力がステップ N+1 の入力として正しく渡される
2. **Domain Service 連携**: 実アルゴリズムが算出した値が Port メソッドに正しい形式で渡される
3. **条件分岐の連携**: ステップ N の結果が null / 空配列の場合にステップ N+1 の振る舞いが正しく変化する

---

### カテゴリ D: カスケード/順序統合

複数のリソースに対する副作用 (作成、更新、削除) が特定の順序で実行されなければならないケース。

**選定条件**:
- 依存リソースの削除順序に制約がある (外部キー制約、論理的な整合性)
- 複数エンティティへの操作の実行順序が要件に定められている

**検証すべきこと**:
1. **実行順序**: 副作用が仕様通りの順序で実行される (記録配列パターンで検証)
2. **認可 + カスケードの結合**: 認可通過後のカスケード処理が全て実行される
3. **認可拒否時の安全性**: カスケード処理の全ステップが未実行である

---

### 統合テストを書かなくてよいケース

- UseCase が単一の Port メソッドを呼ぶだけの単純な CRUD 操作
- Authorization Service のメソッドを 1 回呼ぶだけで、チェーン依存がない認可チェック
- 集約対象が常に 1 件で、計算ロジックが自明な場合
- UseCase 間にデータの受け渡しがなく、それぞれが独立して実行される

---

## 判断基準

1. UseCase の依存に複数の実クラスを経由する協調があるか? → なければ統合テスト不要
2. あれば、ビジネス結果を検証するか (カテゴリ A-1/A-2/A-3) か、技術的パターンか (カテゴリ B/C/D) を判断する
3. 該当カテゴリの選定条件を確認し、対応する検証チェックリストを全て満たすテストを書く

---

## ファイル構造規約

ファイル先頭に JSDoc ブロックを配置し、(1) テスト対象のクラス群とカテゴリ分類、(2) チェーンの呼び出し順序の概要、(3) 単体テストでは検証できない理由、を記載する。

`ChainOverrides` インターフェースを定義し、全フィールドを optional にして必要な Repository のみオーバーライドできるようにする。型は `Parameters<typeof createMockXxxRepository>[0]` で導出する。

`buildChain` ファイルローカル関数で実クラスを手動ワイヤリングして依存ツリーを構築する。戻り値にはアサーションに使う Repository モックも含める。

ファイルスコープの定数として `NOW` (基準日時) と共通テストレコードを定義し、テストケースごとのバリエーションはテストケース内で定義する。

## テスト名の記述規則

| カテゴリ | パターン |
| --- | --- |
| A-1 集約 | `{対象が} {件数} 件のとき {計算結果} を返す` |
| A-2 ルール | `{条件} のとき {評価結果} になる` |
| A-3 連鎖 | `{操作} の後に {関連エンティティ} が {変化内容} に更新される` |
| B 認可通過 | `権限のある {ロール} が {操作} できる` |
| B 認可拒否 | `権限のない {ロール} は AccessDeniedError → {副作用} 未実行` |
| B 前処理 | `存在しない {リソース} は {NotFoundError} (認可チェック前に発生)` |
| C パイプライン | `{step A} の {出力} で {step B} が {処理} を実行する` |
| D 順序 | `{先行操作} の後に {後続操作} が実行される` |

## 制約

### MUST NOT

- 単体テストで検証済みの単一クラス内部ロジックを統合テストで重複検証しない
  理由: 統合テストの目的はクラス間のインタラクション検証であり、単一クラスのロジック検証はユニットテストの責務

- DI コンテナを統合テスト内で使用しない
  理由: DI コンテナを使うとブラックボックスになり、どの依存が実クラスでどれがモックかが不明確になる
  代わりに: 手動ワイヤリングで依存ツリーを構築する

- 実 DB 接続や実 API 呼び出しを行わない
  理由: 外部リソースへの依存はテストの安定性と実行速度を損なう
  代わりに: Port インターフェースのみモックする

- カテゴリ B において認可通過/拒否/前処理順序の 3 パターンを省略しない
  理由: 認可チェーンは 3 パターン全てを検証して初めて安全性が保証される

- カテゴリ A において 0 件・単件・複数件の境界条件を省略しない
  理由: 集約計算は境界条件でバグが発生しやすく、全パターンの検証が必要
