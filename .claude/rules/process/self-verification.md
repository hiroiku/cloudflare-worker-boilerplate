# 自己検証

コード変更を提出する前に、以下の検証を実施する。

---

## 検証チェックリスト

### アーキテクチャ検証

- 変更が依存方向の制約 (外側 → 内側) に違反していないか
- UseCase が Port を介さず直接 I/O していないか
- 外部 SDK の型が UseCase I/O / Port / Domain の公開型に漏洩していないか

### 型安全検証

- `any` 型を使用していないか
- 非 null アサーション (`!`) を使用していないか
- 必要な型ガードが実装されているか

### テスト検証

- 新規ロジックに対応するテストが書かれているか
- TDD のプロセス (Specify → Test + Green → Refactor) に従っているか
- `@throws` ドキュメントに対応するエラーテストがあるか

### 一貫性検証

- 既存のコードパターンと整合しているか
- 命名規約 (camelCase / PascalCase / UPPER_SNAKE_CASE / kebab-case) に従っているか
- ファイル命名規則 (`{名前}.{要素タイプ}.ts`) に従っているか

---

## 信頼度の自己評価

変更の信頼度を以下で評価する。

| レベル | 基準 | アクション |
| --- | --- | --- |
| high | 要件を完全に理解し、影響範囲も把握している | そのまま提出する |
| medium | 要件は理解しているが、影響範囲に不確実性がある | 不確実な箇所を明示して提出する |
| low | 要件や影響範囲に不確実性がある | 再思考し、不確実性を解消してから提出する |

---

## 検証コマンド

### 開発中の検証

テストと実装をセットで書いたら、対象のテストファイルのみを実行して通ることを確認する。

- `vitest run <テストファイルパス>` で対象テストのみ実行する
- 全テスト (`bun run verify`) は開発中には実行しない
  理由: 他エージェントの作業中コードとの干渉を避けるため

### タスク完了時の検証

タスクの全実装が完了したら `bun run verify` を実行し、すべてのチェックを通す。

- `bun run verify` は format + lint + typecheck + test を一括実行する
- warning も error もすべて解消してから完了とする (exit code 0 で成功するまで修正を続ける)
- Linter/Formatter の設定変更による解消は禁止 ([language/common.md](../language/common.md) 参照)
