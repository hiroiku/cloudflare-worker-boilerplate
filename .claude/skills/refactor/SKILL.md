# /refactor スキル

プロジェクトのリファクタリング分析を実行する。6 つの専門エージェントチームが並列で分析し、REFACTORING.md にレポートを保存する。

## 引数の解析

`$ARGUMENTS` を解析する:

- **スコープ**: パスまたは機能名。省略時はプロジェクト全体 (`src/`)
  - 機能名の場合 (例: `goal`): `src/**/{機能名}/**` に展開
  - パスの場合 (例: `src/domain`): そのまま使用
- **`--fix` フラグ**: 指定時は分析後に Critical/Warning を自動修正する。省略時はレポートのみ
- **`--no-resume` フラグ**: 指定時は既存の REFACTORING.md を無視して新規分析を強制する

## 実行フロー

### 1. レジューム検出

REFACTORING.md の存在を Glob で確認する。

**REFACTORING.md が存在し、`--no-resume` が指定されていない場合**:

1. ファイルを Read で読み込み、`[ ]` と `[-]` のチェックボックスを持つ行を集計して残項目数を算出する
2. 残項目がある場合、AskUserQuestion でユーザーに選択肢を提示する:
   - **修正を再開する**: ステップ 8 (レジュームモード) へ
   - **新規分析を実行する**: 既存ファイルを `REFACTORING.backup.md` に Write でコピーし、元ファイルを削除後、ステップ 2 へ
   - **キャンセル**: 「分析をキャンセルしました」と出力して終了
3. 残項目が 0 件の場合 (全て完了済み): ユーザーに「全項目完了済み。`--no-resume` で新規分析を実行できます」と伝えて終了

**REFACTORING.md が存在しない / `--no-resume` が指定されている場合**: ステップ 2 へ進む。

### 2. スコープ確認

Glob で分析対象ファイル数を確認し、ユーザーに報告する。

### 3. チーム組成の判断

- **単一ファイル指定**: チームを組成せず、メインスレッドで全観点を直接分析する (ステップ 4 をスキップしてステップ 5 の処理をメインスレッドで実行)
- **複数ファイル/ディレクトリ/全体**: 以下のチーム組成を実行する

### 4. チーム組成と並列分析

TeamCreate で `refactor-team` を作成する。

各エージェントはコンテキスト分離の原則に従う。各エージェントには自身の分析に必要なルールファイルのみを渡し、他のエージェントの分析結果は共有しない。

次に、6 つの専門エージェント定義ファイルを Read ツールで読み取る:

1. `.claude/agents/refactor-architecture.md`
2. `.claude/agents/refactor-maintainability.md`
3. `.claude/agents/refactor-performance.md`
4. `.claude/agents/refactor-type-safety.md`
5. `.claude/agents/refactor-security.md`
6. `.claude/agents/refactor-test-quality.md`

読み取った各エージェント定義の内容を**プロンプトに含めて** Task ツールで 6 エージェントを**並列** spawn する。
各 Task には以下を設定する:

- `team_name`: `"refactor-team"`
- `subagent_type`: `"general-purpose"`
- `name`: エージェント名 (例: `"refactor-architecture"`)
- `prompt`: エージェント定義ファイルの全文 + 分析対象スコープ + 完了後のレポートをリーダーに SendMessage する指示

TaskCreate で各エージェントにタスクを割り当てる:

- タスクの subject: `"{エージェント名}: {スコープ} の分析"`
- タスクの description: 分析対象スコープの情報

### 5. 結果の収集

全 6 エージェントからの SendMessage を待機する。各エージェントは分析完了後にレポートフォーマットでリーダーに結果を送信する。

### 6. 統合前の自己検証

全エージェントの結果を統合する前に以下を確認する:

- エージェント間で同一問題が重複報告されていないか (例: Architecture と Type Safety が同じ import 違反を報告)
- 重複がある場合、より適切なカテゴリのエージェントの報告を採用し、他方を削除する
- 各エージェントの修正案が互いに矛盾していないか

### 7. REFACTORING.md 書き込みとサマリー出力

全エージェントの結果を統合して Write ツールで REFACTORING.md に書き込む。後述の「REFACTORING.md フォーマット仕様」に従ってフォーマットする。

ユーザーには**統計サマリーテーブルのみ**を出力する (個別の問題詳細は出力しない):

```markdown
## リファクタリング分析完了

**分析スコープ**: {スコープ}
**分析日時**: {日時}
**結果ファイル**: REFACTORING.md

| エージェント    | 分析ファイル数 | Critical | Warning | Suggestion |
| :-------------- | :------------- | :------- | :------ | :--------- |
| Architecture    | N              | X        | Y       | Z          |
| Maintainability | N              | X        | Y       | Z          |
| Performance     | N              | X        | Y       | Z          |
| Type Safety     | N              | X        | Y       | Z          |
| Security        | N              | X        | Y       | Z          |
| Test Quality    | N              | X        | Y       | Z          |
| **合計**        | **N**          | **X**    | **Y**   | **Z**      |

詳細は REFACTORING.md を参照してください。
`/refactor --fix` で自動修正可能な項目を一括修正できます。
```

### 8. 自動修正 (`--fix` 指定時のみ)

`--fix` が指定されている場合:

1. REFACTORING.md を Read で読み込み、`[ ]` で「自動修正可能: はい」の項目を全て抽出する
2. 各項目について:
   a. 対象ファイルを Read で確認し、問題が既に解消されているか確認する
   b. 解消済みの場合: Edit で REFACTORING.md のチェックボックスを `[ ]` → `[x]` に更新して次の項目へ
   c. 未解消の場合: 修正案に基づいて Edit ツールでコードを修正する
   - 機械的に安全な修正に限定する (命名規約、import 整理、パターン準拠、三項演算子の置き換えなど)
   - 設計変更を伴う修正は Edit で `[ ]` → `[-]` に変更し、チェックボックスの後に `<!-- スキップ: 設計変更を伴うため手動対応が必要 -->` を追記する
   - 修正成功後: Edit で REFACTORING.md のチェックボックスを `[ ]` → `[x]` に更新する
3. 全項目の修正後に `bun run verify` を実行して全チェックを通すことを確認する
4. verify が失敗した場合はエラーを修正し、再度 verify を実行する
5. Edit で REFACTORING.md の引き継ぎセクションを更新する
6. 修正内容のサマリーを出力する:
   - 修正済み件数 / スキップ件数 (設計変更) / 解消済み件数の内訳

### 9. レジュームモード修正

チーム組成不要。メインスレッドで既存 REFACTORING.md の残項目を修正する。

1. REFACTORING.md を Read で読み込み、`[ ]` と `[-]` の全項目を抽出する
2. 各項目について:
   a. 対象ファイルを Read で確認し、問題が既に解消されているか確認する
   b. 解消済みの場合: Edit で `[x]` に更新してスキップ
   c. 未解消の場合: 修正案に基づいて Edit ツールでコードを修正する
   - 自動修正可能: はい → 修正して `[x]` に更新
   - 自動修正可能: いいえ → スキップ (引き継ぎセクションに残す)
   - 設計変更を伴う場合: `[-]` のままにして理由コメントを追記
3. `bun run verify` を実行して全チェックを通すことを確認する
4. verify が失敗した場合はエラーを修正し、再度 verify を実行する
5. Edit で REFACTORING.md の引き継ぎセクションを更新する
6. 修正サマリーを出力する

### 10. 後片付け

チームを組成した場合 (ステップ 4 を実行した場合):
全エージェントに shutdown_request を送信し、TeamDelete でチームを解散する。

## REFACTORING.md フォーマット仕様

Write ツールで出力する REFACTORING.md の構造:

```markdown
# リファクタリング分析レポート

**分析日時**: {YYYY-MM-DD HH:mm}
**スコープ**: {スコープ}
**検出件数**: Critical: X / Warning: Y / Suggestion: Z
**自動修正可能件数**: N 件

---

## ステータス凡例

- `[ ]` 未対応
- `[x]` 対応済み
- `[-]` スキップ (設計変更を伴うため手動対応が必要)

---

## Critical (即座に対応が必要)

### [Arch] アーキテクチャ

- [ ] **{問題 ID}: {問題タイトル}** -- `{ファイルパス}:{行番号}`
  - 問題: {具体的な問題の説明}
  - 影響: {放置した場合のリスク}
  - 修正案: {具体的な修正手順}
  - 自動修正可能: はい / いいえ

(以降、同じフォーマットで続く)

### [Maint] 保守性

(同上フォーマット)

### [Perf] パフォーマンス

(同上フォーマット)

### [Type] 型安全性

(同上フォーマット)

### [Sec] セキュリティ

(同上フォーマット)

### [Test] テスト品質

(同上フォーマット)

---

## Warning (早期に対応推奨)

(Critical と同じ構造)

---

## Suggestion (改善提案)

(Critical と同じ構造)

---

## 良好な項目

### [Sec] セキュリティ

- {問題なし / 良好な点の概要}

(その他エージェントの良好項目)

---

## 統計サマリー

| エージェント    | 分析ファイル数 | Critical | Warning | Suggestion |
| :-------------- | :------------- | :------- | :------ | :--------- |
| Architecture    | N              | X        | Y       | Z          |
| Maintainability | N              | X        | Y       | Z          |
| Performance     | N              | X        | Y       | Z          |
| Type Safety     | N              | X        | Y       | Z          |
| Security        | N              | X        | Y       | Z          |
| Test Quality    | N              | X        | Y       | Z          |
| **合計**        | **N**          | **X**    | **Y**   | **Z**      |

---

## 次の AI エージェントへの引き継ぎ事項

- **残件数**: Critical: X / Warning: Y / Suggestion: Z
- **自動修正待ち**: N 件 (`[ ]` + 自動修正可能: はい)
- **手動対応待ち**: N 件 (`[ ]` + 自動修正可能: いいえ)
- **設計変更必要**: N 件 (`[-]`)
- **注意点**: {修正時の注意事項があれば記載}
- **最終更新**: {YYYY-MM-DD HH:mm}
```

## エージェントのレポートフォーマット

各エージェントは以下の構造で結果をリーダーに SendMessage する:

```markdown
## [エージェント名] 分析結果

### Critical (即座に対応が必要)

- **[問題タイトル]** -- `ファイルパス:行番号`
  - 問題: [具体的な問題の説明]
  - 影響: [放置した場合のリスク]
  - 修正案: [具体的な修正手順]
  - 自動修正可能: [はい/いいえ]

### Warning (早期に対応推奨)

- (同上フォーマット)

### Suggestion (改善提案)

- (同上フォーマット)

### 良好な項目

- (問題なしのカテゴリ / 良好な点)

### 統計

- 分析ファイル数: N
- 検出件数: Critical: X, Warning: Y, Suggestion: Z
```

問題が検出されなかったカテゴリは「検出なし」と明記すること。
